1. Überblick und Reihenfolge

Die App ist eine statische Website. GitHub Actions baut sie bei jedem Merge auf main und lädt sie zu Cloudflare Workers hoch. Bis zum Go-Live steht Cloudflare Access davor: Nur freigegebene E-Mail-Adressen kommen mit einem Einmalcode hinein.

Die Reihenfolge ist wichtig. Access (Schritt 8) muss eingerichtet sein, bevor das erste Deployment läuft (Schritt 11). Sonst ist die unfertige App für einige Minuten öffentlich. Der Workflow erkennt das und schlägt fehl, die Seite ist dann aber schon erreichbar.

Schritt Wo Wer Dauer
3–4 Konto und Domain anlegen Cloudflare Entwickler 15 Min.
5 Nameserver umstellen Strato Inhaber des Strato-Kontos 5 Min. + bis zu 24 Std. Wartezeit
6–9 Einstellungen, Access, Token Cloudflare Entwickler 30 Min.
10 Environment, Secrets, Branch-Schutz GitHub Repo-Admin (johannamah) 15 Min.
11 Erstes Deployment GitHub beide (Merge und Freigabe) 10 Min.

3. Cloudflare-Konto anlegen

  1. dash.cloudflare.com/sign-up öffnen und mit einer gemeinsam erreichbaren E-Mail-Adresse registrieren. Am besten nimmt man eine Funktionsadresse statt eines privaten Postfachs, denn an diese Adresse gehen Sicherheitsmeldungen.
  2. E-Mail-Adresse bestätigen.
  3. Zwei-Faktor-Anmeldung einschalten: Profil (oben rechts) → My Profile → Authentication → Two-Factor Authentication → Authenticator-App. Den QR-Code im gemeinsamen Passwortmanager hinterlegen. Die Wiederherstellungscodes ebenfalls dort ablegen.

Ein gemeinsames Konto ist laut ADR-0012 eine Übergangslösung. Später lassen sich unter Manage Account → Members persönliche Zugänge einladen. Spätestens nach der Tagung sollte das Konto an den Verein übergehen.

4. Domain zu Cloudflare hinzufügen

  1. Im Dashboard Add a domain (bzw. Websites → Add a site) wählen und altstipendiaten-jahrestagung.de eingeben. Die Option „Quick scan for DNS records" aktiviert lassen.
  2. Tarif Free wählen.
  3. Cloudflare zeigt die gefundenen DNS-Einträge. Jetzt aufräumen:
    • Löschen: alle A-, AAAA- und CNAME-Einträge für altstipendiaten-jahrestagung.de (Name @) und für www. Sie zeigen auf Strato-Server und würden das Deployment blockieren. Den Eintrag für die Domain legt das erste Deployment selbst an.
    • Behalten: MX- und TXT-Einträge (E-Mail, SPF, DKIM), falls E-Mail über die Domain läuft. Mit dem Bildschirmfoto aus Strato vergleichen. Fehlt einer, von Hand ergänzen.
  4. Cloudflare zeigt zwei Nameserver, etwa xxx.ns.cloudflare.com und yyy.ns.cloudflare.com. Beide genau abschreiben. Sie sind für jedes Konto anders.

5. Nameserver bei Strato umstellen

Strato ändert seine Oberfläche gelegentlich, die Menünamen können abweichen. Gesucht ist immer die Einstellung für Nameserver bzw. externe Nameserver der Domain.

  1. Im Strato-Kunden-Login anmelden und das Paket mit der Domain wählen.
  2. Domains → Domainverwaltung.
  3. Bei altstipendiaten-jahrestagung.de auf das Zahnrad bzw. Verwalten klicken.
  4. Falls DNSSEC aktiv ist: zuerst ausschalten. Sonst ist die Domain nach dem Umzug nicht mehr erreichbar.
  5. Den Reiter bzw. Punkt Nameserver öffnen → Nameserver ändern → Eigene Nameserver verwenden. Die beiden Cloudflare-Nameserver aus Schritt 4 eintragen und alle übrigen Felder leeren.
  6. Speichern und die Sicherheitsabfrage bestätigen.
  7. In Cloudflare auf der Seite der Domain Check nameservers now klicken. Sobald die Domain als Active erscheint (meist innerhalb einer Stunde, höchstens 24 Stunden), kommt eine E-Mail.

Bietet Strato bei eurem Paket keine eigenen Nameserver an, bitte beim Strato-Support nach „externen Nameservern für eine .de-Domain" fragen. Ein Umzug der Domain zum Cloudflare-Registrar geht nicht, Cloudflare bietet .de nicht an.

Prüfen lässt sich die Umstellung im Terminal:

dig NS altstipendiaten-jahrestagung.de +short

Erwartet: die beiden *.ns.cloudflare.com-Einträge.

7. Weiterleitung von www

Maßgeblich ist die Adresse ohne www. Damit www. überhaupt bei Cloudflare ankommt, braucht es einen Platzhalter-Eintrag:

  1. DNS → Records → Add record: Typ AAAA, Name www, IPv6 100::, Proxy status Proxied (orange Wolke). Die Adresse 100:: ist absichtlich ein Nirgendwo: Cloudflare beantwortet die Anfrage selbst.
  2. Rules → Overview → Create rule → Redirect Rule (bzw. Rules → Redirect Rules). Die Vorlage „Redirect from WWW to Root" wählen. Sie leitet mit Status 301 um und behält Pfad und Parameter. Speichern.

Prüfen, sobald die Zone aktiv ist:

curl -sI https://www.altstipendiaten-jahrestagung.de/programm/ | grep -iE "^(HTTP|location)"

Erwartet: 301 und location: https://altstipendiaten-jahrestagung.de/programm/.

8. Cloudflare Access für die Vorabphase

  1. Im Dashboard links Zero Trust öffnen. Beim ersten Mal den Teamnamen aus Schritt 2 eingeben und den Tarif Free wählen. Cloudflare verlangt dafür eventuell ein Zahlungsmittel, berechnet bis 50 Nutzer aber nichts.
  2. Settings → Authentication → Login methods: Prüfen, dass One-time PIN vorhanden ist. Es ist voreingestellt und schickt einen Code per E-Mail. Weitere Methoden sind nicht nötig.
  3. Access → Applications → Add an application → Self-hosted:
    • Application name: Jahrestagung Vorabzugang
    • Session duration: die Sitzungsdauer aus Schritt 2 (Empfehlung: 1 week)
    • Public hostname 1: Subdomain leer, Domain altstipendiaten-jahrestagung.de, Path leer
    • Public hostname 2: Subdomain www, gleiche Domain, Path leer
  4. Policy anlegen: Name Freigegebene Personen, Action Allow, Include → Selector Emails → die Adressen aus der Liste des Orga-Teams einzeln eintragen. Tipp: Unter Access → Access groups eine Gruppe anlegen und in der Policy nur die Gruppe verwenden, dann pflegt man die Liste an einer Stelle.
  5. Speichern.

Prüfen

curl -sI https://altstipendiaten-jahrestagung.de/ | grep -iE "^(HTTP|location)"

Erwartet: 302 und eine location auf …cloudflareaccess.com. Das funktioniert schon vor dem ersten Deployment.

Bekannte Einschränkungen in der Vorabphase:

  • „Zum Startbildschirm hinzufügen" funktioniert nur eingeschränkt: Der Browser lädt das App-Manifest ohne Anmeldung und bekommt nur die Weiterleitung.
  • Läuft die Sitzung ab, liefert der Service Worker zunächst die zwischengespeicherten Seiten. Neue Inhalte gibt es erst nach erneutem Einloggen.

Beides entfällt mit dem Go-Live.

9. API-Token und Account-ID

API-Token

  1. My Profile → API Tokens → Create Token, Vorlage „Edit Cloudflare Workers" → Use template.
  2. Einschränken: Account Resources → Include → genau dieses Konto. Zone Resources → Include → Specific zone → altstipendiaten-jahrestagung.de.
  3. TTL: ein Ablaufdatum setzen, z. B. Ende Juni 2027, nach der Tagung. Ein Token ohne Ablauf vergisst man.
  4. Continue to summary → Create Token. Das Token wird nur einmal angezeigt. Direkt in GitHub eintragen (Schritt 10) und zusätzlich im Passwortmanager ablegen.

Account-ID

Workers & Pages öffnen. Die Account ID steht rechts in der Seitenleiste, alternativ auf der Übersichtsseite der Domain unter API. Sie ist kein Geheimnis, wird aber trotzdem nur in GitHub hinterlegt.

10. GitHub einrichten

Das braucht Admin-Rechte am Repository, also johannamah. Ein Account mit reinem Schreibzugriff sieht die Einstellungen nicht.

Environment production

  1. Settings → Environments → New environment, Name genau production.
  2. Required reviewers: beide Entwickler eintragen, Prevent self-review anhaken. So kann niemand seinen eigenen Merge allein live schalten.
  3. Deployment branches and tags: Selected branches → Regel main.
  4. Environment secrets → Add secret: CLOUDFLARE_API_TOKEN = Token aus Schritt 9.
  5. Environment variables → Add variable:
    • CLOUDFLARE_ACCOUNT_ID = Account-ID aus Schritt 9
    • VORABZUGANG = aktiv. Damit prüft der Workflow nach jedem Deployment, dass Access davorsteht. Fehlt die Variable, gilt ebenfalls aktiv.
  6. Nur falls die Zugangsabfrage aus ADR-0010 bleiben soll: Secret ZUGANGSWORT. Empfehlung: weglassen.

11. Erstes Deployment

Voraussetzungen: Schritte 3 bis 10 erledigt und die Zone ist Active.

  1. Die PRs in dieser Reihenfolge reviewen und mergen: #16 (Jetztkarte) → danach bei #17 und beim Deployment-PR die Basis auf main umstellen → #17 (Datenschutz) → Deployment-PR.
  2. Actions → Deployment zeigt den Job „Produktion" als Waiting. Die andere Person öffnet ihn → Review deployments → production → Approve and deploy.
  3. Der Job prüft, baut, deployt und ruft die Adresse ab. Beim ersten Mal legt Cloudflare dabei den DNS-Eintrag und das Zertifikat an. Das kann ein bis zwei Minuten dauern.

12. Go-Live (geplant Anfang Dezember 2026)

Erst wenn alles aus „Vom Vorstand" in Schritt 2 erledigt ist und das Go vorliegt:

  1. PR mit den letzten Textänderungen: Platzhalterhinweis der Datenschutzerklärung entfernen, Datum der Fassung eintragen. Danach mergen und deployen, noch hinter Access.
  2. GitHub → Environment production → Variable VORABZUGANG auf aus setzen.
  3. Cloudflare → Zero Trust → Access → Applications → „Jahrestagung Vorabzugang" → Delete.
  4. GitHub → Actions → Deployment → Run workflow (Branch main) und freigeben. Die Prüfung erwartet jetzt Status 200, die richtige Cache-Kopfzeile für /sw.js und die www-Weiterleitung.
  5. Im privaten Fenster ohne Anmeldung öffnen und die Seiten durchklicken.

Die Reihenfolge von Schritt 2 und 3 ist egal, solange danach ein Deployment läuft. Steht VORABZUGANG noch auf aktiv, wenn Access schon entfernt ist, schlägt die Prüfung fehl. Das ist gewollt, denn genau diese Abweichung soll auffallen.

13. Fehlerbehebung

Meldung Ursache und Abhilfe
Authentication error [code: 10000] Token falsch, abgelaufen oder ohne Rechte für Konto bzw. Zone. Neues Token nach Schritt 9 erzeugen und das Secret ersetzen.
„Hostname … already has externally managed DNS records" Ein alter A/AAAA/CNAME-Eintrag für die Domain liegt noch in Cloudflare (Strato-Import). Unter DNS → Records löschen, Job neu starten.
„Could not find zone" Zone ist noch nicht Active. Nameserver bei Strato prüfen (Schritt 5).
„Vorabzugang ist aktiv, aber … antwortet ohne Anmeldung mit 200" Die App ist öffentlich. Sofort die Access-Anwendung prüfen: Hostname richtig? Policy gespeichert? Bis dahin notfalls das Deployment zurückrollen (Schritt 14) oder unter Domains & Routes die Domain entfernen.
„/sw.js wird zwischengespeichert" public/_headers wurde nicht übernommen. Prüfen, ob die Datei in dist/ landet, und ob eine Cache Rule in Cloudflare die Kopfzeile überschreibt.
„www leitet nicht dauerhaft … weiter" Schritt 7: AAAA-Eintrag (Proxied) und Redirect Rule prüfen.
Job „Produktion" startet nicht Wartet auf Freigabe (Schritt 11) oder lief nicht auf main.
Zertifikatsfehler im Browser direkt nach dem ersten Deployment Das Zertifikat wird noch ausgestellt. Einige Minuten warten.

14. Laufender Betrieb

Zurück auf einen früheren Stand

Am schnellsten im Dashboard: Workers & Pages → altstipendiaten-jahrestagung → Deployments → bei einer früheren Version Rollback. Danach den Fehler per PR beheben. Das nächste Deployment von main überschreibt den Rollback.

Freigegebene Personen ändern

Zero Trust → Access → Access groups (oder die Policy) bearbeiten. Das wirkt sofort, ohne Deployment.

Token erneuern

Vor Ablauf ein neues Token nach Schritt 9 erzeugen, das Secret in GitHub ersetzen und das alte Token in Cloudflare löschen. Dasselbe gilt sofort, wenn jemand ausscheidet oder das Token irgendwo sichtbar geworden ist.

Nach der Tagung

Klären, wer Konto und Domain übernimmt (offene Frage F2). Die Domain-Verlängerung bei Strato läuft weiter, auch wenn niemand mehr die App pflegt.
